The agent that searched once: agentic RAG, counted

Give a small model a search tool and permission to use it as often as it likes, and it searches once, in 30 runs out of 30. It beats one-shot RAG by one answer in thirty, at 2.7 times the tokens, and both score zero on the questions that need a second search.

By Shimon R. Malka

24 November 20269 min readRetrievalAgent loopsEvaluation

Agentic RAG comes with a pitch: retrieval-augmented generation (Lewis et al., 2020) retrieves once and hopes, but an agent searches until it knows. It rewrites a bad query, follows a lead from one document to the next, and stops when it has the answer. A 2025 survey (Singh et al.) describes agents that plan, reflect and refine their retrieval over several rounds. The pitch is about behaviour, and behaviour can be counted. This post counts it.

The Building AI Agents course has a study for exactly this question. The same 30 questions are answered twice by the same small local model: once by one-shot RAG, and once by an agent that may search as often as it likes. The short version: the agent searched once. Not once on average. Once, in every one of its 30 runs.

The set-up

The document store belongs to a fictional manufacturer, Acme: policies, product sheets, support articles, supplier profiles and meeting notes, cut into passages with ids like p0158. A labelled set of 100 questions comes in four styles: identifier ("AW-2075 warranty"), lexical (the corpus's own words), paraphrase (the user's words, not the corpus's) and multi, which needs two documents. "What payment terms do we have with the company that supplies the parts for the Lever Widget Pro?" needs the product sheet to name the supplier, then the supplier's profile to give the terms. No single query retrieves both.

Thirty questions are drawn at random from the hundred, and each is answered in two modes, with qwen3:4b on a laptop:

  • rag is a workflow: search once with the question, paste the top five passages into the prompt, make one model call.
  • agent is a loop: the model gets a search_corpus tool and chooses what to search for, how often and when to stop. Its budget is six model calls, so it has room for five searches and an answer.

Both modes use the same retriever: hybrid search over BM25 and a dense index, each with the passage title prepended, fused by reciprocal rank, five passages per search. The agent's instructions do not leave the behaviour to its imagination:

Use the search_corpus tool to find passages, and search again with other words if the results do not answer the question.

An answer is correct when it matches the question's lenient answer pattern (finance director, or \b45\b for a number). Both modes must cite passages as [p0123], and every run records each id that any search returned, so a citation of an id the run never saw is caught by set difference.

It searched once

Every agent run made exactly two model calls: one that issued a search, and one that answered. Not one of the 30 used a second search, although the budget allowed four more. In four runs the agent wrote that the results did not answer the question, which is the exact condition its instructions gave for searching again, and in all four it stopped. Two of those were the multi-hop questions, which are the reason to build an agent in the first place.

On the Lever Widget Pro question the agent searched for "Lever Widget Pro parts supplier payment terms", got back the product sheet that names the supplier, Lyon Laiton, and answered that the results do not specify the payment terms for Lyon Laiton. The next step was a search for one name it had just read. It wrote the name down and stopped. On the Rivet Widget S question it searched for "Rivet Widget S", got the product specification and warranty passages, and reported that they "do not include payment terms with suppliers". Both modes scored 0 of 2 on multi-hop. One-shot RAG has the excuse that it cannot search twice. The agent had no excuse, only the habit.

The freedom to search again is a sentence in a prompt. Whether the model uses it is a property of the model. Self-RAG (Asai et al., 2023) trains a model to decide when to retrieve. ReAct (Yao et al., 2022), which interleaves reasoning with calls to a Wikipedia search API, was measured on far larger models. A prompted four-billion-parameter model is neither, and it behaved like a workflow with an extra model call.

What the one search bought

Where did the extra answer come from, then? From the one search being a different search. The agent wrote its own query in 24 of the 30 runs: every lexical, paraphrase and multi question, and 2 of the 8 identifier ones. That rewording is the whole effect, in both directions.

The third row is the instructive one. Dropping "Which error is this?" looks like tidying, and it removed the only words that pointed at an error-code article. Rewriting a query is a bet that the model knows the corpus's vocabulary better than the user does, and a model that has never seen the corpus is guessing.

By style, both modes were perfect on identifier (8 of 8) and lexical (9 of 9) questions. Every difference between them is on paraphrase, where rag scored 8 of 11 and the agent 9 of 11. That is where query rewriting should help, and it did, by one question net.

The price

The agent's median run used 1,934 tokens against rag's 723, 2.7 times as many; summed over the 30 runs the ratio is 3.0. Its median run took 26.5 seconds against 8.2. Both costs have the same cause: one search means two model calls, and the second re-sends the first.

Split the tokens and the shape is clear. Prompt tokens grow 2.4 times (median 849 against 347), because the second call carries the instructions, the first call and the five passages again. Completion tokens grow 3.3 times (median 1,116 against 338), because each of the two calls thinks before it speaks, and qwen3:4b spends its thinking as output tokens, the expensive kind on a hosted API. Completion is 63% of the agent's tokens. The course's E3 lesson on budgets derives the growth formula; this is its two-step case, and the agent paid it for one search it could have been handed.

What 30 paired questions can tell you

Not much about the score, and that is worth knowing before the run, not after it.

Pairing helps. On 27 of the 30 questions the two modes agreed, right or wrong, so the comparison lives in the 3 that disagreed: 2 went to the agent and 1 to rag. The exact McNemar test asks whether a 2 to 1 split is surprising for a fair coin, and the answer is p = 1.000. It is not a small effect that failed to reach significance. It is no evidence at all.

The resolution is set by the number of questions. With 30, the smallest difference that can clear p < 0.05 is six disagreements, all going the same way: a 6 to 0 split gives p = 0.031, and 5 to 0 gives 0.062. Six questions in thirty is 20 points. A smaller difference, in either direction, cannot be told from noise at this size, however the questions fall. In a simulation where 10% of questions disagree and the agent wins two in three of them, which is what this run saw, it takes about 750 questions to detect the difference four times in five.

Behaviour is different. "Searched once in 30 of 30 runs" is not a comparison, it is a count, and it needs no test to be true of these runs. It can still be bounded: zero second searches in 30 runs is consistent with a true rate of up to about 11% (Wilson, 95%). That is enough to say the loop is mostly idle. It is not enough to say it never runs.

And two multi-hop questions are two anecdotes. They show the failure clearly; they say nothing about its rate. The full set holds five, which is also too few. If multi-hop is the reason for the agent, it needs its own sample.

The citations held, mostly

No answer in either mode cited an id it had not retrieved: zero fabricated citations in 60 runs. One agent answer cited nothing, because it said it had found nothing. That check is cheap, mechanical and worth running in production, because a model that has seen the format can write p0159 as easily as p0158.

The labelled check is weaker than it looks. The agent's right answer on surface finishing cited a passage from Gent Coatings' supplier profile, but not the one labelled as gold: it cited the delivery-performance passage, whose title names the supplier and whose text mentions colour matching, so "cites gold" scored a right answer as a miss. Whenever the store holds more than one passage that can answer and the labels mark one, "cites gold" undercounts. The same answer shows the opposite gap: the passage it cited never says that Gent Coatings does surface finishing. Neither check establishes that a cited passage supports the sentence beside it. That needs an entailment judgement: RAGAS (Es et al., 2023) asks a model whether each statement in an answer can be inferred from its context, which is a model grading a model.

Is your agent using its loop?

Agentic RAG is sold on what the loop does. Check that it does it:

  • Count searches per run, and read the distribution. A mean of 1.4 can be most runs searching once and a few searching five times. A distribution that is all ones is a workflow that costs twice as much.
  • Look at multi-hop questions separately, and have enough of them. They are where the loop should earn its price, and in a general question set they are a few percent. Two will show you a failure; thirty will give you a rate.
  • Log the queries the agent writes. In this study the rewording was the entire effect, good and bad. You cannot see that in a score.
  • Pair the comparison and know its resolution first. Same questions, both modes, McNemar on the disagreements. With 30 questions, anything under 20 points is a reason to run more, not a finding.
  • Split the tokens into prompt and completion. With a thinking model, every extra call pays for thinking as well as for re-sent context.
  • Check citations by set difference. Cited and never retrieved is a fabrication, and it costs one line to catch.

If the counts say the model will not take the second step, code can take it. IRCoT (Trivedi et al., 2022) interleaves retrieval with each reasoning step, because what to retrieve next depends on what has been worked out so far; a workflow that extracts the supplier's name and searches for it is a few lines of ordinary code. Neither was measured here; both are cheaper to try than a bigger model.

What the study leaves out

  • A bigger model. Four billion parameters with thinking on, one prompt. A frontier model may well search twice. That is the point of counting: you find out for your model, rather than assuming it from a diagram.
  • Other prompts. One instruction, which already asked for a second search. A prompt that demands a plan before the first search may change the count. It is a cheap experiment, and the count is how you would score it.
  • The grader. A lenient answer pattern accepts a right number beside a wrong reason. Both modes face the same pattern, which keeps the comparison fair and the absolute scores generous.

The study is part of the retrieval and memory module of Building AI Agents, where the learner builds both modes, the citation check and the retriever, and runs the comparison on their own laptop. The agent loop underneath it is in the free preview, starting with workflows and agents.
