E3 · שיעור 02

כלי הוא סכמה, פונקציה והודעת שגיאה, והמודל קורא שניים מהם

לכלי יש שלושה חלקים. הפונקציה היא החלק היחיד שהמודל אף פעם לא רואה. השניים האחרים הם טקסט שהוא קורא: הסכמה (schema), שאומרת מה מותר לו לבקש, והודעת השגיאה, שאומרת מה השתבש כשביקש לא נכון. בלולאה הזו, הקוד שאתם כותבים והמודל קורא חשוב יותר מהקוד שעושה את העבודה.

הסכמה היא פרומפט

מודול 1 שיעור 8 הראה את הפרומפט המרונדר: השם, התיאור וסכמת הפרמטרים של כל כלי עוברים סריאליזציה לתור המערכת, והמודל קורא אותם כמו כל טקסט אחר. לכן לסכמה יש שני תפקידים. היא תיעוד, שהמודל יכול לציית לו או להתעלם ממנו, והיא חוזה, שרק הקוד שלכם יכול לאכוף. אחד הכלים של המעבדה:

{"type": "function", "function": {"name": "send_email", "description": "Send an e-mail.",
  "parameters": {"type": "object",
    "properties": {"to": {"type": "string", "description": "Recipient address."},
                   "subject": {"type": "string", "description": "Subject line."},
                   "body": {"type": "string", "description": "Plain-text body."}},
    "required": ["to", "subject", "body"]}}}

שום דבר כאן לא מונע מהמודל לכתוב {"to": "manager@acme.example", "subject": "Q3" ולגמור את הטוקנים לפני הסוגר המסולסל. Gorilla (Patil et al., 2023) מדדו את הגרסה הכללית של הבעיה: אפילו המודלים החזקים ביותר של אותה תקופה כתבו ארגומנטים שגויים והמציאו שימושים ב־API בתדירות כזו, שמודל שעבר fine-tuning על תיעוד API ניצח אותם. שני כשלים דורשים טיפול שונה.

כשל 1: בכלל לא JSON

שרתי Chat Completions שולחים את arguments כמחרוזת JSON, ולכן ייתכן שהיא לא תעבור פענוח. הלולאה של מודול 1 עושה את זה:

args = json.loads(args) if isinstance(args, str) else args   # agent/agent.py

מחרוזת פגומה זורקת JSONDecodeError, וכל הריצה מתה בלי לדווח על כלום. loop/schema.py מחזיר את הכשל כדאטה במקום זאת:

>>> parse_arguments('{"path": "notes/q3-report.txt",}')
(None, "arguments are not valid JSON: Expecting property name enclosed in double quotes at character 31")
>>> parse_arguments("")
({}, None)                  # some servers send "" for a call with no arguments

כשל 2: JSON, אבל לא מה שהסכמה ביקשה

SEND היא הגרסה של הבדיקה לסכמה של send_email, עם תוספת של "additionalProperties": false:

>>> check_arguments(SEND, {"to": "x", "subject": 3, "cc": "boss"})
["missing required field 'body'", "'subject' must be string, got integer",
 "unexpected field 'cc' (allowed: body, subject, to)"]

check_arguments מכסה את החלק של JSON Schema שהגדרות כלים משתמשות בו: type, properties, required, additionalProperties: false, enum ו־items. את השאר, כמו pattern ו־format, היא מתעלמת מהם ולא נכשלת עליהם. שני פרטים קל לפספס. ב־JSON Schema 3.0 הוא integer ו־true אינו, ואילו ב־Python True == 1, כך שבדיקה תמימה של isinstance(v, int) מקבלת ערך בוליאני בתור ספירה. ובלי additionalProperties: false, שדה שהסכמה לא מונה עובר. ה־send_email של המעבדה למעלה לא מגדיר אותו, ולכן {"to": ..., "subject": ..., "body": ..., "cc": "boss@acme.example"} עובר את הבדיקה, והכלי מתעלם בשקט מנמען שהמודל חשב שהוסיף. בשדה אופציונלי, שגיאת כתיב ("subjcet") עוברת באותה דרך. הדקו את הסכמות שבבעלותכם. באלה שלא, הבדיקה יכולה לאכוף רק את מה שכתוב בהן.

הודעת השגיאה היא הפרומפט השני

שתי השגיאות חוזרות למודל כתוצאה של הכלי, בהודעת tool שנושאת את ה־id של הקריאה, והכלי לא רץ. ה־id אינו אופציונלי. שרתי Chat Completions מצפים שכל קריאה בתור של assistant תיענה בהודעת tool עם ה־id שלה, ורבים מהם דוחים את הבקשה הבאה אם אחת חסרה. קריאה שנדחתה ונעלמת בשקט גם משאירה את המודל בטוח שהיא רצה:

ERROR: send_email: invalid arguments: missing required field 'body'.

ההודעה הזו היא המידע היחיד של המודל על מה שהשתבש, אז כתבו אותה לקורא שיפעל לפיה מיד. שלושה כללים:

  1. ציינו את השדה ואת התיקון. «invalid arguments» לבד מייצר שוב את אותה קריאה. «missing required field 'body'» מייצר קריאה עם body.
  2. פרטו את החלופות. כלי לא מוכר מקבל את רשימת הכלים האמיתיים: ERROR: no tool named 'email_send'. Available: list_files, read_file, ....
  3. לעולם אל תתנו לפונקציה לרוץ על ארגומנטים שנכשלו בבדיקה. כלי ש«עושה כמיטב יכולתו» עם {"to": 3} קיבל החלטה שהמודל לא ביקש.

כמה פעמים זה משנה? על עשרים משימות המעבדה, qwen3:4b כתב ארגומנטים תקינים ותואמי סכמה בכל 120 הריצות (הבנייה): אף קריאה לא נדחתה, אף קריסה. מודל קטן עם רשימה של שלושה־עשר כלים מצליח לייצר את הצורה הנכונה. הבדיקות הן ליום שבו הוא לא יצליח: רשימת כלים ארוכה יותר, מודל מכומת (quantised), תשובה קטועה, או סכמה עם enum שהמודל מעולם לא ראה. הכשלים הנדירים האלה הם אלה שמפילים לולאה שרצה בלי השגחה בשלוש לפנות בוקר.

איפה הסכמה לא יכולה לעזור

סכמה בודקת צורה, לא משמעות. {"to": "attacker@evil.example", "subject": "Q3", "body": "..."} עובר כל כלל שלמעלה. האם הנמען הזה מותר זו שאלה של מדיניות, ומודולים 3 ו־13 שמים אותה בשער הבקרה (gateway), שם הסוכן לא יכול לשכתב אותה. חלק מהספקים מציעים מצב strict שמגביל את הפענוח (decoding) לסכמה, כך שאי אפשר לייצר ארגומנטים פגומים (E2 שיעור 4). זה מעלים את כשל 1, ואת כל כשל 2 שהסכמה מבטאת, במידה שמצב ה־strict של הספק תומך במילות המפתח שלה. את בעיית המשמעות זה לא מעלים בכלל.

בדקו את עצמכם

  1. הסכמה של כלי מגדירה את count כ־{"type": "integer"}. אילו מבין 3, 3.0, "3", true עוברים, ולמה התשובה לגבי true שונה בין JSON Schema לבין בדיקה תמימה ב־Python?
  2. למה קריאה שנדחתה צריכה עדיין לייצר הודעת tool עם ה־id של הקריאה, במקום להיעלם בשקט?
  3. התיאור של הכלי שלכם אומר "date in ISO 8601", אבל הסכמה אומרת רק {"type": "string"}. מודל שולח "next Tuesday". איזו שכבה צריכה לתפוס את זה, ומה השגיאה צריכה לומר?
תשובות
  1. 3 ו־3.0 עוברים: JSON Schema מתייחס לכל מספר בלי חלק שברי כ־integer. "3" נכשל (מחרוזת), וכך גם true (בוליאני). בדיקה תמימה ב־Python של isinstance(v, int) מקבלת את True, כי bool הוא תת־מחלקה של int, ולכן הבדיקה חייבת להוציא ערכים בוליאניים במפורש.
  2. המודל ביקש את הקריאה הזו ומחכה לתוצאה שלה. בלי תוצאה שנושאת את אותו id, בבקשה הבאה יש תור assistant עם קריאה שלא נענתה. יש שרתים שדוחים את זה על הסף, ובכל מקרה המודל נאלץ לנחש אם הקריאה קרתה. תוצאת השגיאה אומרת לו בדיוק מה קרה.
  3. קוד, לא בדיקת הסכמה של הלולאה הזו. הסכמה אומרת רק "type": "string", ומילות המפתח שהיו יכולות לומר יותר, pattern ו־format, הן כאלה ש־check_arguments מתעלמת מהן. לכן הפרסר של הכלי עצמו (או הרחבה של הבדיקה) חייב לתפוס את זה, עם שגיאה שמציינת את הפורמט: 'date' must be ISO 8601 (YYYY-MM-DD), got 'next Tuesday'. התיאור לבדו הוא בקשה, לא בדיקה.
