JSON פשוט, והמפענחים שלו עדיין חלוקים

מדיניות אומרת «לחסום כל קריאה שה־amount שלה עולה על 1,000». מפענח ה־JSON של שער הבקרה (gateway) שומר את ה־amount הראשון; זה של שירות התשלומים שומר את האחרון. התוקף שולח {"amount": 10, "amount": 1000000} ושער הבקרה קורא 10. שום דבר לא פגום; שתי תוכניות תקינות קוראות טקסט אחד בשתי דרכים.

הדקדוק נכנס על כרטיס

ל־JSON יש שישה סוגי ערכים: אובייקט, מערך, מחרוזת, מספר, true/false, null (RFC 8259, 2017). מפתחות הם מחרוזות, מחרוזות מוקפות במירכאות כפולות, אין הערות ואין פסיקים בסוף רשימה. הקיצור הזה הוא הסיבה שזו השפה של הסוכנים: ארגומנטים של כלים, תשובות של מודלים והודעות MCP הם JSON.

מה הדקדוק משאיר פתוח

RFC 8259 משאיר חמישה מקומות למימוש, ובכל אחד מהם שני מימושים יכולים להיות שונים. Python 3 מראה את שני הראשונים, ואת חשבון הנקודה הצפה שמאחורי השני, בארבע שורות:

import json
print(json.loads('{"amount": 1, "amount": 1000000}'))   # {'amount': 1000000}
print(json.loads('{"n": 1e400}'))                      # {'n': inf}
print(json.loads('{"n": 12345678901234567890}'))       # exact in Python; a double in JavaScript
print(0.1 + 0.2)                                       # 0.30000000000000004
נקודה פתוחה מה שונה מה תוקף עושה עם זה
מפתחות כפולים «The names within an object SHOULD be unique», ואם לא, ההתנהגות לא צפויה: הראשון מנצח, האחרון מנצח, או שגיאה שולח שני ערכים; הבקרה קוראת אחד, הכלי את השני
טווח מספרים מספרים שלמים גדולים ו־1e400 הופכים ל־inf, ל־double מעוגל או לשגיאה מגבלה שנבדקת כ־9007199254740993 ומבוצעת כ־...992
מחרוזות \u0000, surrogates בודדים, Unicode בנרמול שונה שם שלא שווה לשום ערך ב־allow-list ומוביל לאותו קובץ
עומק וגודל אין מגבלה מוגדרת מערך עמוק שמפיל מפענח אחד ולא את השני
טיפוס "1" הוא מחרוזת, 1 הוא מספר "amount": "1000000" שצד אחד ממיר בשקט

הכלל שהקורס פועל לפיו

מחליטים על אותם בתים שמעבירים הלאה, אחרי פענוח במפענח שדוחה כל דבר דו־משמעי. מודול 3 שיעור 6 בונה את זה: שער הבקרה דוחה כל אובייקט עם מפתח שחוזר, ומעביר הלאה את הצורה שהוא סידר מחדש (re-serialised) ועליה החליט, לא את הבתים המקוריים. כך המפענח היחיד ששירות הכלים פוגש הוא זה של שער הבקרה.

מומחה: צורה קנונית היא חובת הוכחה

«לסדר מחדש» סוגר את הפער רק אם פענוח ואחריו סידור הוא דטרמיניסטי, לא מאבד שום דבר שהכלי קורא, והמפענח שבהמשך קורא את הפלט כמו ששער הבקרה קרא אותו. RFC 8785 (JSON Canonicalization Scheme) קיים כי חתימות על JSON צריכות את התכונה הזו; לרוב שערי הבקרה מספיקה תכונה חלשה יותר: שבפלט אין מפתחות כפולים, ושהמספרים בו בטווח ששני הצדדים מסכימים עליו. אמרו במפורש באיזו מהן אתם טוענים.

בדקו את עצמכם

  1. למה «שער הבקרה מפענח עם מפענח קפדני» לא מספיק אם הוא מעביר הלאה את הבתים המקוריים?
  2. שדה עשרוני "risk": 0.1 מסוכם עשר פעמים ומושווה ל־1.0. מה תהיה התוצאה, ומה זה אומר על שימוש בנקודה צפה לכסף?
  3. כלי מקבל {"path": "notes/café.txt"}, ושער הבקרה משווה את המחרוזת המפוענחת ל־allow-list. בעזרת שורת המחרוזות בטבלה, תארו ערך JSON תקין שני שההשוואה מתייחסת אליו כשונה, ומערכת קבצים עשויה לפתוח כאותו קובץ.
תשובות
  1. קפדנות מתקנת רק את הקריאה של שער הבקרה עצמו. הכלי עדיין מפענח את הבתים המקוריים במפענח שלו, ובכל קלט שבו השניים שונים (טווח מספרים, צורות Unicode, המרת טיפוסים) שער הבקרה החליט על ערך שהכלי לעולם לא רואה. רק העברת הצורה המסודרת מחדש הופכת את הקריאה של שער הבקרה לזו שהכלי מקבל.
  2. חיבור 0.1 עשר פעמים בלולאה נותן 0.9999999999999999, כך ש־== 1.0 הוא False ובדיקה בדיוק על הגבול מתהפכת. ל־0.1 אין ייצוג בינארי מדויק והשגיאות מצטברות; כסף שייך ליחידות משנה שלמות (אגורות, סנטים) או לטיפוס עשרוני, אף פעם לא לנקודה צפה.
  3. "notes/café.txt": e ואחריו סימן הטעמה המשולב (U+0301), לעומת ה־é המורכב מראש (U+00E9) שבמקור. שתי המחרוזות שונות בנקודות הקוד, ולכן ההשוואה מול ה־allow-list נכשלת, בעוד מערכת קבצים שמנרמלת שמות פותחת את אותו קובץ.
