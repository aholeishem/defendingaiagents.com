OAuth נותן לטוקן ייעוד: תפקידים, scope, קהל יעד

סוכן צריך לקרוא רשומה של לקוח אחד. ה־CRM לא אמור למסור לסוכן סיסמה, וגם לא לסמוך עליו עם כל הלקוחות. OAuth הוא אוצר המילים לזה: מי מבקש, מי מחליט, מי מנפיק, מי מגיש, ולמה הטוקן נועד.

ארבעה תפקידים

OAuth 2.0 מגדיר ארבעה תפקידים (RFC 6749, 2012):

תפקיד בפריסה של סוכן מה עושה
בעל המשאב (resource owner) האדם (או הארגון) שהדאטה שלו מתיר או מסרב
לקוח (client) הסוכן, או שער הבקרה (gateway) שפועל בשמו מבקש טוקן ומציג אותו
שרת הרשאות (authorization server) ספק הזהויות (identity provider) מאמת, מחיל מדיניות, מנפיק טוקנים
שרת משאבים (resource server) ה־CRM, היומן, שרת MCP מאמת את הטוקן ומגיש את הבקשה

שרת המשאבים אף פעם לא רואה סיסמה ואף פעם לא מדבר עם המשתמש של הלקוח. הוא בודק טוקן מול המנפיק שהוא סומך עליו.

מה בדרך כלל טוקן של סוכן

שתי זרימות (flows) מכסות את הקורס הזה:

  • Authorization code (עם PKCE, RFC 7636): אדם מתחבר בשרת ההרשאות ונותן הסכמה; הלקוח מקבל טוקן שפועל בשם האדם הזה. מנגנון ההרשאה של MCP משתמש בזה.
  • Client credentials (RFC 6749, סעיף 4.4): אין אדם. הלקוח מאמת את עצמו בתור עצמו ומקבל טוקן שנושא את שם הלקוח. זה סוכן עם זהות משלו (מודול 12, שיעור 1).

שלושה שדות, שלוש מגבלות

שדה מגביל שגוי אם
scope אילו פעולות (crm:read) הוא *, או נושא יותר ממה שהמשימה צריכה
aud איזה שרת מקבל אותו חסר, או שכל שרת מקבל את הטוקן
sub (ושרשרת השחקנים, actor chain) למי מיוחסת הפעולה הוא שם של חשבון שירות משותף שחמישים סוכנים משתמשים בו

מזהי משאבים (resource indicators, RFC 8707, 2020) מאפשרים ללקוח לציין את קהל היעד (audience) בבקשה, ולשרת ההרשאות לשים אותו ב־aud. החלפת טוקנים (token exchange, RFC 8693, 2020) מאפשרת לשירות להמיר טוקן אחד בטוקן אחר עם scope צר יותר וקהל יעד אחר. כך שער בקרה יכול להחזיק טוקן לעצמו ולמסור ל־CRM טוקן שנוצר בשביל ה־CRM. הטוקן המוחלף יכול לשאת טענת act (actor) שנותנת שם לגורם שפועל בשם sub, מקוננת פעם אחת לכל קפיצה, כך ש«שער הבקרה, בשם agent-7, בשם דנה» כתוב בטוקן ולא מוסק מהיומנים. הקינון הזה הוא שרשרת השחקנים מהטבלה שלמעלה.

מומחה: scope הוא בקשה, לא הבטחה

לקוח מבקש scopes; שרת ההרשאות מעניק את מה שהמדיניות שלו מתירה, וטוקן עשוי לשאת פחות ממה שביקשו. שרת משאבים שמניח שה־scope המבוקש הוענק, בדק את המשאלות של הלקוח שלו. מלכודת שנייה: scope משמעותי רק כמו השרת שמפרש אותו. שני שרתים שקוראים שניהם read יכולים להתכוון לדברים שונים. ושלישית: החלפת טוקן שמרחיבה. החלפה מותר לה רק לצמצם; מודול 12 בונה ובודק את הבדיקה הזו.

בדקו את עצמכם

  1. מפו את התפקידים בהגדרה הזו: אדם מבקש מסוכן עוזר «לסכם את הטיקטים הפתוחים שלי»; הסוכן קורא לשרת MCP של מערכת טיקטים דרך שער הבקרה שלכם.
  2. לטוקן יש aud = שער הבקרה. שער הבקרה צריך ששרת הטיקטים יקבל את הקריאה. מהן שתי הדרכים הנכונות להשיג טוקן ששרת הטיקטים יקבל, ומהי הדרך השגויה?
  3. scope: crm:read ו־aud: crm. מה משניהם מונע שימוש חוזר (replay) בטוקן הזה מול היומן, ומה מונע ממנו למחוק רשומה ב־CRM?
תשובות
  1. בעל המשאב: האדם שהטיקטים שלו. לקוח: הסוכן העוזר, כששער הבקרה פועל בשמו בקריאה היוצאת. שרת הרשאות: ספק הזהויות שבו האדם מתחבר ונותן הסכמה (authorization code עם PKCE, כי הטוקן פועל בשם האדם הזה). שרת משאבים: שרת ה־MCP של מערכת הטיקטים.
  2. נכון: שער הבקרה מחליף את הטוקן שלו בטוקן עם aud = שרת הטיקטים ו־scope צר יותר (token exchange, RFC 8693, עם טענת act שנותנת את שם שער הבקרה); או שהלקוח מבקש משרת ההרשאות טוקן לשרת הטיקטים ישירות, ומציין אותו בתור המשאב (RFC 8707). שגוי: להעביר את הטוקן של שער הבקרה כמו שהוא, ולגרום לשרת הטיקטים לדלג על בדיקת קהל היעד או לרכך אותה.
  3. aud: crm מונע replay מול היומן, שאינו קהל היעד. scope: crm:read מונע את המחיקה ב־CRM, שאינה קריאה. כל אחד מהם עובד רק אם השרת שמקבל את הטוקן בודק אותו.
