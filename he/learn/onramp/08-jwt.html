מסלול הכנה · שיעור 08

JWT הוא טענות חתומות, ולבדיקה יש סדר

שרת מקבל Authorization: Bearer eyJhbGciOi…. הוא מפצל לפי נקודות, מפענח base64 את החלק האמצעי, קורא "role": "admin" ומעביר את הקריאה. את החלק השלישי הוא לא בדק אף פעם. את הטוקן כתב הקורא, לפני דקה, בעורך טקסט.

שלושה חלקים, שניים מהם סתם JSON

ל־JSON Web Token (JWT) יש שלושה חלקים בקידוד base64url, מחוברים בנקודות: header, payload (הטענות, claims) וחתימה (signature) (RFC 7519, 2015; RFC 7515, 2015). הפענוח אינו סוד: base64url הוא קידוד, לא הצפנה. זה טוקן אמיתי שהונפק עם מפתח חד־פעמי, והספרייה הסטנדרטית קוראת אותו:

import base64, json
tok = ("eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9."
       "eyJpc3MiOiJodHRwczovL2F1dGguYWNtZS5leGFtcGxlIiwic3ViIjoiYWdlbnQtNyIsImF1ZCI6Imh0dHBzOi8vY3JtLmFjbWUuZXhhbXBsZS9tY3AiLCJzY29wZSI6ImNybTpyZWFkIiwiaWF0IjoxMDAwLCJleHAiOjEzMDB9."
       "2Vc6vcSxz-JiNHCGQqh18ZrUCUKVOqZghKK27YDicRo")
part = lambda s: json.loads(base64.urlsafe_b64decode(s + "=" * (-len(s) % 4)))
print(part(tok.split(".")[0]))   # {'alg': 'HS256', 'typ': 'JWT'}
print(part(tok.split(".")[1]))
# {'iss': 'https://auth.acme.example', 'sub': 'agent-7', 'aud': 'https://crm.acme.example/mcp',
#  'scope': 'crm:read', 'iat': 1000, 'exp': 1300}
טענה שם משמעות
iss issuer (מנפיק) מי הנפיק וחתם
sub subject (נושא) על מי הטוקן (כאן סוכן, לא אדם)
aud audience (קהל יעד) איזה שרת רשאי לקבל אותו
exp, iat, nbf תפוגה, הנפקה, לא לפני חלון הזמן, בשניות מאז 1970
scope scope (היקף) מה הוא מתיר (RFC 9068 נושא אותו בטוקני גישה של OAuth)

החתימה קושרת את שני החלקים הראשונים

החתימה מחושבת על header.payload עם מפתח. HS256 משתמש בסוד משותף אחד (HMAC-SHA-256): כל מי שיכול לאמת יכול גם לזייף. RS256 ו־ES256 משתמשים במפתח פרטי לחתימה ובמפתח ציבורי לאימות, כך ששרת משאבים (resource server) יכול לבדוק טוקנים בלי יכולת להנפיק אותם. שנו תו אחד ב־payload, והחתימה מפסיקה להתאים.

הבדיקה, לפי הסדר

המאמת שלמטה הוא הקצר ביותר שעדיין הגון (HS256 בלבד). הסדר שלו הוא השיעור:

import hashlib, hmac

def verify(tok, key, aud, now):
    h, p, s = tok.split(".")
    if part(h)["alg"] != "HS256":                       # 1. the algorithm we configured
        raise ValueError("algorithm")
    good = base64.urlsafe_b64encode(
        hmac.new(key, f"{h}.{p}".encode(), hashlib.sha256).digest()).rstrip(b"=").decode()
    if not hmac.compare_digest(good, s):                # 2. the signature
        raise ValueError("signature")
    c = part(p)
    if c["iss"] != "https://auth.acme.example":         # 3. the issuer
        raise ValueError("issuer")
    if aud not in ([c["aud"]] if isinstance(c["aud"], str) else c["aud"]):   # 4. the audience
        raise ValueError("audience")
    if c["exp"] <= now:                                 # 5. the time
        raise ValueError("expired")
    return c                                            # 6. only now read sub and scope

המספרים שלמטה הם השלבים שלו:

  1. אלגוריתם: זה שאתם הגדרתם, אף פעם לא זה שה־header של הטוקן מבקש.
  2. חתימה: לחשב מחדש ולהשוות בזמן קבוע.
  3. מנפיק: המנפיק שאתם סומכים עליו.
  4. קהל יעד: אתם בתוכו (מודול 3, שיעור 10).
  5. זמן: exp בעתיד; לאפשר סטיית שעון של שניות, לא דקות.
  6. רק אז לקרוא את sub ואת scope.

כשמריצים אותו עם המפתח b"demo-key-not-a-secret", הוא מקבל את הטוקן שלמעלה בזמן t = 1100 עבור קהל היעד https://crm.acme.example/mcp, ודוחה את ארבעת אלה, מהסיבות האלה:

מה הוצג נדחה בגלל
ל־https://cal.acme.example/mcp קהל יעד
בזמן t = 1300 פג תוקף (exp לא כולל את עצמו)
payload ששונה ל־crm:write, עם החתימה המקורית חתימה
header {"alg": "none"}, בלי חתימה אלגוריתם

מומחה: כל המתקפות גרות בשלב 1

alg: none הוא אלגוריתם תקף לפי ה־RFC, ופירושו «לא מאובטח». ספרייה שמכבדת אותו מקבלת טוקן שאף אחד לא חתם עליו. המתקפה השנייה היא בלבול מפתחות (key confusion): השרת מצפה ל־RS256 ומאמת עם המפתח הציבורי שלו; התוקף קובע alg: HS256, חותם עם המפתח הציבורי בתור סוד ה־HMAC, וספרייה שבוחרת את האלגוריתם לפי ה־header מאמתת אותו. JWT Best Current Practices (RFC 8725, 2020) מונה את שתיהן ואת התרופה: לנעוץ אלגוריתם לכל מפתח, ולדחות כל דבר אחר. שני פרמטרים ב־header מזמינים את אותה טעות: kid (באיזה מפתח להשתמש) ו־jku (URL שממנו מושכים קבוצת מפתחות). מאמת שהולך אחרי אחד מהם כפי שהטוקן אומר, נתן לטוקן לבחור את השופט שלו.

בדקו את עצמכם

  1. שרת מחזיק מפתחות של שני מנפיקים ומקבל חתימה של כל אחד מהם. למה טוקן עם "role": "admin" שחתום בידי המנפיק השני מסוכן לו יותר מטוקן בלי חתימה בכלל, ואיזה שלב עוצר אותו?
  2. שרת מאמת את החתימה ואת exp אבל לא את aud, ושרת הרשאות (authorization server) אחד מנפיק טוקנים ל־20 שרתי משאבים שכולם מדלגים על הבדיקה. בכמה שרתים אפשר להשתמש מחדש (replay) בטוקן שנגנב מאחד מהם, לפני שהוסיפו את שלב 4 ואחרי?
  3. מאמת קורא את alg מהטוקן ובוחר לפיו פונקציה מהספרייה. תארו, במשפט אחד כל אחת, את none ואת בלבול המפתחות נגדו.
תשובות
  1. טוקן בלי חתימה נכשל בשלב 1 או 2 בכל מאמת תקין. טוקן שחתום בידי המנפיק השני עובר את שלב 2, כי לשרת יש את המפתח הזה, ולכן "role": "admin" מגיע ונראה אמיתי. שלב 3 עוצר אותו, בתנאי שהמנפיק נבדק מול המפתח שאימת את החתימה: טוקן שחתום במפתח של B אבל טוען iss A חייב להיכשל.
  2. לפני: בכל ה־20, כי כל אחד מהם מאמת את החתימה של אותו שרת הרשאות ואף אחד לא בודק את קהל היעד. אחרי שלב 4: באחד, השרת ששמו מופיע ב־aud; ואם הטוקן נגנב מהשרת הזה עצמו, באף מקום אחר.
  3. none: התוקף קובע "alg": "none", שולח חתימה ריקה, והמאמת קורא לפונקציית «לא מאובטח» שלו, שמקבלת טענות שאף אחד לא חתם עליהן. בלבול מפתחות: לשרת יש מפתח ציבורי של RS256; התוקף קובע "alg": "HS256" וחותם עם המפתח הציבורי הזה בתור סוד ה־HMAC, והמאמת, שמריץ HMAC עם המפתח שבידו, מוצא שהחתימה תקפה.
