Module 00 · At scale: thousands of agents, nobody's inventory

At scale: thousands of agents, nobody's inventory

Your laptop has one agent, written by you, with thirteen tools: ten lab tools plus three CRM tools over MCP. A large organisation has something like this:

  • Hundreds to thousands of agents, built by different teams on different frameworks, plus agents inside every SaaS product it buys, plus coding agents on most developers' laptops.
  • No complete list of them. Ask a security team how many agents their company runs and the honest answer is a range. Module 19 calls this the denominator problem, the first number an auditor asks for, and Module 20 estimates it with an interval.
  • Shared credentials. An API key created for one prototype ends up in five agents. When something goes wrong, the log says "the key did it".

Why the boundary becomes shared infrastructure

You cannot put a carefully built control inside each of a thousand agents, owned by a hundred teams, half of them bought. You can put one at the place their tool calls pass through:

Interception point Sees Misses
A gateway or proxy for tool and API traffic Every call routed through it Calls that are not routed through it
A sidecar next to each agent workload Everything that workload sends Agents not deployed on that platform
A hook in the coding agent on each laptop Commands before they run Laptops without the hook
The SaaS vendor's own controls Their agent's actions Anything you cannot configure

Each row trades coverage for depth. That is why the miniature gateway you build sits at the tool call: it is the one component that still makes sense when multiplied by a thousand. Module 3 returns to where it lives and what it costs in latency; Module 21 to what happens when it is slow or down.

A first estimate

Suppose 2,000 agents average 25,000 tool calls a day each: 50 million calls a day, about 580 a second on average and a few times that at peak. Hold that number. In Module 4 you will time your detector on your laptop and find out how many cores it would need.

Check yourself

  1. A gateway sees 100% of routed traffic. What determines how much of the organisation's agent traffic it sees, and how would you estimate that share?
  2. The 580 calls a second is an average. Which single assumption in the estimate is least certain, and how would a factor-of-ten error in it change what you build?
Answers
  1. Routing: the share of the organisation's agents whose tool calls pass through it, which excludes agents on other platforms, inside bought SaaS and on unhooked laptops. Estimating it needs the denominator: count agents from independent sources (egress logs, model-provider billing, API keys in use) and compare with what the gateway sees, as Module 20 does with an interval.
  2. The number of agents, 2,000: nobody has a complete list, and the honest answer is a range. A factor of ten moves the average between 58 and 5,800 calls a second (with peaks a few times higher). At 58 a heavier, per-call detector on a single host is affordable; at 5,800 every millisecond and core per call multiplies, and the gateway has to scale out.
