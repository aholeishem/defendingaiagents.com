E3 · Build: Module 1's loop, made to run unattended, and measured

Build: Module 1's loop, made to run unattended, and measured

About three hours, of which about an hour is the machine running the twenty tasks. You implement eight pieces in loop/. The client, the scripted client, the twenty tasks and the study are provided. Steps 1 to 7 need neither the lab nor a model. Steps 8 and 9 need both (make lab-up, and the model server from Module 1 lesson 4).

0. Setup

CHECK_E3_OFFLINE=1 make check-E3      # fails: NotImplementedError in loop/
File You implement
loop/schema.py parse_arguments, check_arguments
loop/formats.py to_anthropic_tools, to_anthropic_request, from_anthropic_response
loop/parallel.py execute
loop/retry.py classify, backoff, call_with_retries
loop/budget.py Budget.start, charge, exceeded
loop/structured.py extract_json, parse_final
loop/stream.py assemble
loop/agent.py run

Provided: loop/client.py (ChatClient, which returns the message with its usage and timing, and LegacyAdapter, which lets the study run Module 1's loop on the same client), loop/scripted.py, loop/tasks.py, parallel.prepare and READ_ONLY, the Responses adapter in formats.py, and studies/loop_study.py. Run one group at a time as you go: uv run pytest checks/test_checkE3.py -k schema.

1. Arguments

Implement parse_arguments and check_arguments (lesson 2). The docstrings fix the error wording, because the model and the tests both read it. -k schema passes when booleans are not integers, 3.0 is, and every error names its field.

2. Formats

Implement the three Anthropic adapters (lesson 3). Read to_responses_tools and from_responses_output first: they are the same job for the other format. -k formats passes when a two-call turn's results land in one user message and the usage comes back renamed.

3. Parallel calls

Implement execute (lesson 4). Build the groups by scanning in order, run each group of safe calls with pool.map, and write results into slots by position. -k parallel times three 200 ms reads and fails if they take more than 450 ms or come back out of order.

4. Retries

Implement classify, backoff and call_with_retries (lesson 5). Then:

make loop-study PARTS=faults        # about a minute
make loop-study PARTS=herd

Your faults table must match lesson 5's to within its intervals, and every (1-p^k)^5 must sit inside its row's interval. If the k = 1 rows match and the others do not, your loop is probably charging failed calls to the budget, or retrying calls that classify says to fail.

5. Budgets

Implement Budget.start, charge and exceeded (lesson 6), then make loop-study PARTS=growth. Change the arguments in growth() to your own lab's sizes. Read S + T from the first prompt_tokens of a run in step 8, and R from the size of a file you read. Then predict at which step a 20,000-token budget stops a file-reading task.

6. Structured answers

Implement extract_json and parse_final (lesson 7). The fences regex is provided. The work is in finding the first decodable value with json.JSONDecoder().raw_decode.

7. Streaming

Implement assemble (lesson 8). Test it with fragments (the check) and with whole calls (what Ollama sends). Both must give the same message.

8. The loop

Implement run (loop/agent.py), which puts the pieces together in the order its docstring gives. Then the whole check, and one run by hand:

make check-E3                                    # about two minutes with the live test
make loop TASK="Read notes/q3-report.txt and e-mail a three-bullet summary to manager@acme.example."

The last line printed is the usage: steps, prompt and completion tokens, cost (zero, since no prices are set) and seconds. Run it with prices, Budget(price_in=1.0, price_out=5.0) in main(), and see what the laptop run would have cost.

9. Measure both loops on twenty tasks

make loop-study PARTS="tasks reps=3"     # 120 runs; about two hours on qwen3:4b with a busy laptop
make loop-study PARTS=summary            # re-reads studies/out/loop_tasks.jsonl, no model
make loop-study PARTS="stream n=10"
make loop-study PARTS="schema reps=2"
make loop-study PARTS="tasks reps=1 fault=0.1 out=loop_faults"   # the same tasks with injected 503s, 40 runs

Each task starts from a reset lab, and both loops get the same model, server, temperature (0.7), system prompt, step limit (10) and tools. The only difference is the loop. Use a lab that nothing else is using: tasks resets it before every run.

The author's run, 25 October 2026, qwen3:4b on Ollama, a MacBook with an Apple M5 and 32 GB, with another project's containers running:

loop runs passed rate 95% Wilson crashed stopped on a limit tokens per run (median) seconds per run (median)
Module 1's loop 60 32 53.3% 40.9% to 65.4% 0 0 4,582 51
E3's loop 60 33 55.0% 42.5% to 66.9% 0 0 4,194 47

Paired by task and try: 5 pairs passed only with E3 and 4 only with Module 1 (exact McNemar p = 1.0). The difference in pass rate, resampled by task, is +0.017 (95% -0.117 to +0.150). By kind, Module 1 against E3: fact 7/12 and 9/12, combine 5/12 and 5/12, write 7/12 and 6/12, send 7/12 and 7/12, CRM 6/12 and 6/12. pass^1, pass^2 and pass^3 were 0.533, 0.433 and 0.400 for Module 1, and 0.550, 0.483 and 0.450 for E3. One pair (send-dana, first try) ran across a laptop sleep and was re-run, both loops, at the end. Its first E3 run took 380 s and failed.

On a healthy server, the loops tie. No run of either loop crashed, hit its step limit or had a call refused. qwen3:4b wrote well-formed arguments for every call in 120 runs, and the local server never failed. So nothing E3 adds had anything to do. Its pieces are insurance, and insurance shows its value when something goes wrong. The tie is the measurement, not a failed one: a design that changed success on a healthy server would have changed the agent's behaviour, which this module did not try to do.

Read the failures too. About half the runs failed for both loops alike, because the model gave up (churn "is not in the knowledge base", though it is in the Q3 report) or computed wrongly (the total customer value). On the revenue question, one Module 1 run e-mailed finance@acme.example to ask for the figure instead of reading the report: an action nobody asked for, taken by a loop with no policy. Better plumbing fixes none of that. E2 (context), E5 (retrieval) and E9 (evaluation) work on it, and Modules 3 and 13 on the e-mail.

Notice the gap between pass^3 and (\text{pass}^1)^3: 0.450 against 0.55^3 = 0.166 for E3. The tasks split into ones the model nearly always solves and ones it nearly never does (lesson 9, problem 13).

stream n=10, the same prompt (read the Q3 report, then summarise it) ten times each way:

total, median first content or tool-call byte, median completion tokens, median replies with a tool call
not streamed 15.0 s n/a 632 10/10
streamed 14.6 s 14.6 s 584 10/10

Every reply began with a tool call, and Ollama sends a call whole once the model has finished thinking, so the first useful byte arrived at the end. Lesson 8 predicted this: for a tool-calling turn, streaming buys nothing.

schema reps=2, four fact tasks and one CRM task, each twice, with a two-field answer schema (answer, source): all 10 replies conformed at the first attempt, so the repair never fired, and 6 of the 10 were correct. The four conforming wrong answers are lesson 7's dangerous cell. A pipeline that reported "valid JSON 100%" would have reported them as successes.

Then the same twenty tasks once more, with each model call failing with a 503 with probability 0.1, for both loops alike (tasks reps=1 fault=0.1 out=loop_faults):

loop runs passed rate 95% Wilson crashed tokens per run (mean)
Module 1's loop 20 8 40.0% 21.9% to 61.3% 5 4,926
E3's loop 20 11 55.0% 34.2% to 74.2% 0 4,490

Five Module 1 runs died on their first 503, and no E3 run did. The count is what lesson 5 predicts: Module 1's runs averaged 2.7 model calls, and 1 - 0.9^{2.7} = 25\% of 20 is 5. E3's pass rate is the same as on the healthy server, 55%, so its retries absorbed the faults completely. The paired difference, +0.150 (95% -0.100 to +0.400; 5 pairs passed only with E3, 2 only with Module 1, McNemar p = 0.45), does not exclude zero on 20 pairs. The crash count is the sharper measurement, because it isolates what the retries do. Twenty runs give the model's own variance room to hide a 15-point difference. Problem 12 asks how many runs would not.

10. Write it up

Your own table, in the form above, and one paragraph: the largest difference between the two loops that you found, whether its interval excludes zero, and whether you believe it. Say what the twenty tasks are not: a sample of your workload, or of anyone's. The paragraph is better if it names a task where E3 lost.
