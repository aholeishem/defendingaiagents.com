Here is the agent loop most first agents ship with:

def run(task, client):
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}]
    while True:
        reply = client.complete(messages, TOOLS)
        messages.append(reply.message)
        if not reply.message.get("tool_calls"):
            return reply.message.get("content")
        for call in reply.message["tool_calls"]:
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": run_tool(call["function"]["name"], call["function"]["arguments"])})

It works in the demo. It has two properties that the demo never shows: the first time the model server answers 503, the run dies, and if the model never decides it is finished, neither does the loop. This post puts that loop behind a server that fails one call in ten and measures what happens as the obvious fixes go in, one at a time. The short version: retries fix the crashes and reveal something worse, and an outage that used to cost a few failed runs starts costing ten times the tokens.

The set-up

The measurement comes from a lab. A finance team wants an assistant that answers questions from its files: the total of Acme's invoices, the city of customer C-103, the number of invoices for September. It has three tools, list_files, read_file and search_files, and twelve tasks. Ten have an answer in the files. Two do not: the contracts with Hooli and Pied Piper do not exist, and a good agent says so and stops.

The model is simulated: fixed, readable behaviour, so that every difference in the numbers comes from the loop and none from chance. Like a real model, it sometimes asks for customers when the file is customers.csv, and when it cannot find something it keeps searching with new phrasings. In front of it sits a server that fails 10% of calls, the way a busy model API does: mostly 503 Service Unavailable, and one failure in four a 429 Too Many Requests with Retry-After: 2. Every task runs three times, 36 runs in all, and the failures are seeded, so every version of the loop meets exactly the same outages. A guard stops any run at 60 model calls, so that a loop with no limit cannot hang the measurement.

Stage A and B: the outage is the only brake

Stage A gets 6 of 36 right, mostly because the model asks for files by the wrong name and the tool answers error: no such file: customers. That says what went wrong and nothing about how to fix it. Stage B changes only the message, to suggest the nearest file names, and the score goes from 6 to 22 without touching the loop. A tool's error message is a prompt; it deserves the same care as one.

Then the crashes. A task that needs n model calls, each failing independently with probability p, survives with probability (1 − p)n. The answerable tasks average about 3.2 calls, so 1 − 0.93.2, about 29%, of naive runs should crash. The measurement: 8 of 30 answerable runs, 27%.

The other six crashes are the interesting ones. All six runs of the two impossible tasks crashed, every time, on a 503 or a 429. Nothing else would have stopped them: the model keeps searching for a contract that does not exist, and the loop has no reason to object. In stage B, the server outage is the agent's only budget.

Stage C: retries, done properly

Retrying is the right response to a 503, and the lab does it by the book. First, classify: not every failure is worth repeating.

FailureRetry?Why
Timeout, refused connectionyestransient by nature
429 Too Many Requestsyes, after Retry-Afterthe server said "later"
500, 502, 503, 504yesoverloaded or restarting
400, 401, 403, 404, 422nothe same request fails the same way every time
A KeyError in your own codenoa bug: retrying hides it

The last row matters more than it looks. A policy that retries every exception turns a bug in your adapter into four slow failures and a report that the server is unreliable. And the status code is not always enough: Anthropic's API documentation notes that a 429 caused by reaching a spend cap carries no Retry-After and keeps failing until access resumes, and OpenAI's rate-limit guide says not to retry quota or billing errors at all.

Second, back off with full jitter: wait a random time between zero and min(cap, base × 2n) before attempt n. Exponential backoff alone keeps a herd of clients that failed together in step, retrying together at 0.5 s, 1 s, 2 s. Marc Brooker's analysis on the AWS Architecture Blog is the standard reference. In the course's own simulation of 1,000 clients failing at the same instant, the busiest 100 ms at the first retry held all 1,000 requests without jitter and 211 with full jitter.

Third, honour Retry-After (RFC 9110, section 10.2.3; RFC 6585 for 429), as a minimum: wait the larger of the server's figure and the backoff draw. OpenAI's guide gives the same advice: treat the value as a floor and add a little randomness. Fourth, cap the attempts: four in all, then raise the last error.

With all four, the crashes go from 14 to 0, and the right answers from 22 to 30. Then the other columns. Model calls go from 144 to 466. Tokens go from 78,957 to 803,126, ten times as many, and six runs never stop.

Nothing is wrong with the retries. They did exactly their job: they removed the outage that was killing the impossible tasks, and now those tasks search until the guard stops them at 60 calls. Each of those calls re-sends the entire conversation, because the model keeps no state between calls, so a run's prompt tokens grow roughly with the square of its length. The six runaway runs account for 753,503 of the 803,126 tokens: 94% of the bill, for zero answers.

In this lab the guard is a test fixture. In production there is no guard. There is an invoice.

Retries multiply

The lab retries at one level. Real systems rarely do. The Google SRE book's chapter on cascading failures points out that retries at several layers multiply: one request at the top can become the product of every layer's attempts at the bottom. An SDK that retries by default, inside a loop that retries, inside a job runner that retries, turns one 503 into dozens of calls aimed at a server that is already struggling. OpenAI's guide makes the same point about SDK retries nested inside your own. The SRE book's remedies are the ones the lab uses, plus one: limit the attempts per request, and keep a retry budget across requests, so that when a large share of calls are failing the client stops adding load. Its overload chapter describes a per-client budget that allows retries only while they are under 10% of requests.

OpenAI's guide adds a detail that makes blind retries worse than useless: unsuccessful requests count towards the per-minute limit. Retrying a 429 at once spends quota on the act of being refused.

Stage D: budgets, checked before every call

The fix is a budget the loop checks before each model call, with four limits and the name of the one that stopped the run:

LimitCountsProtects against
stepsmodel callsthe loop that never stops
tokensprompt and completion, summed over the runthe context that grows every step
costtokens at a price per millionthe bill
secondswall clock since the run startedthe user who is waiting, and the server that is retrying

The lab's defaults are 12 steps, 20,000 tokens and 120 seconds. With them, all 36 runs end, 36 are right, nothing crashes and nothing runs away. The two impossible tasks stop on their step limit after 12 calls and say they found nothing, rather than inventing a contract. The total is 105,804 tokens, less than a seventh of the stage C figure.

Two details are easy to get wrong. "At the limit" means out: with a limit of 3 steps, three calls leave no room for a fourth, so the check has to come before the call, not after it. And a step is not a unit of cost. One step can send 600 tokens and the next 6,000, so a step limit alone is not a budget.

The finished loop uses more tokens than the naive one, 105,804 against 78,957. That is the correct result. It finishes the runs the naive loop abandoned, and finishing costs tokens. The aim was never to spend less than a crash; it was to spend a known, bounded amount.

Why this is a security problem

OWASP's Top 10 for LLM Applications 2025 lists Unbounded Consumption as LLM10, and names denial of wallet among its risks: an attacker who exploits the cost-per-use model of AI services to run up a bill. Its listed mitigations include rate limiting, timeouts and resource-allocation management, which is to say budgets. The lab needed no attacker: an ordinary outage and an honest model were enough to multiply the token count by ten. An attacker who can make a task unanswerable, by planting a document that sends the agent looking for something that does not exist, gets the same effect on purpose.

The 503 test

Before an agent runs unattended, put it behind a server that fails one call in ten, and count. Specifically:

  • Classify before you retry. Timeouts, 429 and 5xx: retry. Other 4xx and your own exceptions: fail at once, and loudly.
  • Back off with full jitter, and honour Retry-After as a minimum. Cap the attempts, and retry at one layer only.
  • Budget steps, tokens, cost and time, checked before every call. Report which one stopped the run, so that a stopped run is never mistaken for an answer.
  • Include a task that has no answer. It is the only kind that shows whether your loop knows how to stop.
  • Read the token column, not just the success column. Stage C scored 30 of 36 with no crashes, and looks like progress until the bill arrives.

One caveat the lab does not hide: a failed call costs no tokens, so it is never charged to the budget, and the time limit is checked only between calls. A server that times out at 30 seconds, retried three times, will carry a run past a 120-second limit before the loop gets a chance to look. A time budget that should cut a retry sequence short has to be passed into the retry code itself.
